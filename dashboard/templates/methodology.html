Methodology & Risk Model

1. Mosca's Inequality

Urgency is governed by Mosca's inequality (Mosca, IEEE S&P 2018). An asymmetric cryptographic deployment is in danger of “Harvest Now, Decrypt Later” (HNDL) attacks when:

X + Y > Z
  • X (Security / Shelf Life): The number of years the encrypted data must remain confidential.
  • Y (Migration Time): The number of years required to transition systems, libraries, and certificates to post-quantum cryptography.
  • Z (Quantum Horizon / Collapse Time): The estimated years until a cryptanalytically relevant quantum computer (CRQC) becomes capable of breaking classical public-key cryptography.

Rearranged, the safe window remaining after migrating is safe window = Z - Y. If data must remain confidential beyond that window (X ≥ Z - Y), the host is high risk today.

2. Cryptographic Classification Rules

Every scanned host is categorized into one of five cryptographic classes based on its negotiated TLS handshake and certificate:

Cryptographic algorithm classification rules and criteria
Class Definition Handshake Criteria Default Migration Step
▲ vulnerable Classical asymmetric cryptography only Classical key exchange (e.g., X25519, P-256, RSA) and/or classical certificate (RSA, ECDSA). Replace classical key exchange with ML-KEM or hybrid X25519MLKEM768; plan certificate migration.
✓ hybrid Combination of post-quantum and classical algorithms PQ-hybrid key exchange (e.g., X25519MLKEM768, SecP256r1MLKEM768) with classical or hybrid certificate. No immediate action needed; monitor standardization and complete certificate chain upgrade.
✓ resistant Full post-quantum protection Pure post-quantum key exchange (ML-KEM) and post-quantum certificate (ML-DSA / Falcon). Fully protected against quantum cryptanalysis; maintain regular standard reviews.
◆ weakened Weak symmetric encryption or hashing Legacy ciphers (e.g., 3DES, RC4, AES-128, SHA-1). Upgrade to AES-256 and SHA-2 / SHA-3 to preserve 128-bit security against Grover's algorithm.
? unknown Handshake error or unclassified cipher Connection timeout, TLS alert, or unrecognized cipher suite. Manual review of host configuration and reachability.

3. Planning Scenarios & Defaults

QuantumAudit structures planning assumptions into parameter triplets formatted as x{X}_y{Y}_z{Z}.

The default planning scenario is x15_y3_z15 (configured default: {{ default_scenario }}):

  • X = 15 years: Long-term commercial or government confidentiality requirement.
  • Y = 3 years: Typical enterprise software and infrastructure migration duration.
  • Z = 15 years: Conservative consensus horizon for a CRQC capable of breaking RSA-2048 / ECC-256.

Under this default scenario, safe window = 15 - 3 = 12 years. Because X (15) ≥ 12, classical vulnerable hosts are flagged as high risk.

Contextual vs Naive Baseline: A naive rule flags every classical host as high risk regardless of data lifespan. QuantumAudit's contextual model evaluates the actual shelf life against the safe window, avoiding alert fatigue for short-lived data.

4. Limitations & Ethical Boundaries

  • Handshake Only: The scanner only completes the standard TLS handshake to inspect server hello and certificate messages. It never issues HTTP requests, accesses application routes, or stores user payloads.
  • Temporal Snapshot: Public scans (e.g., Tranco top domains) represent a point-in-time observation. Server configurations and cipher suites change over time; random seeds ensure sample selection reproducibility rather than perpetual world state.
  • Controlled Lab Testing: All synthetic attack and migration simulations run in an isolated Docker environment with zero production impact.
  • Decision Support Prompt: Risk verdicts are designed as an executive prioritization aid to guide cryptographic agility, not as an exhaustive vulnerability audit.
