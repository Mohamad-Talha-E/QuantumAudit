QuantumAudit

TLS-driven post-quantum migration planning

A TLS handshake shows what a server uses. It does not show what to migrate first. QuantumAudit adds explicit planning assumptions, measures the cost, and shows which verdicts change.

What it does

  1. Looks. The scanner completes two handshakes per host. Python ssl gives the certificate fields. OpenSSL 3.5 gives the group, protocol, cipher and post-quantum support.
  2. Scores. A rule uses Mosca's inequality with stated inputs. A naive baseline flags every classical host. Both are stored with a reason and a next step.
  3. Measures. A controlled lab benchmarks ML-KEM, ML-DSA, classical algorithms and hybrid TLS 1.3 on time and bytes.
Risk whenX + Y > Z X = data shelf life · Y = migration time · Z = quantum horizon

Experiments

ExperimentQuestionMeasured result
E1Is the scanner accurate?20/20 laboratory rows exact. Precision, recall and F1 = 1.00.
E2What is deployed?73 of 100 hosts answered. 44 used hybrid X25519MLKEM768. No ML-DSA certificate.
E3How fast are the algorithms?ML-KEM-768 encapsulation 0.0237 ms. ML-DSA-65 signing 0.7117 ms.
E4What does hybrid TLS cost?+0.8% time. +80.9% bytes versus classical TLS 1.3.
E5What happens under constraint?Half a CPU and 256 MB roughly halve throughput for every algorithm.
E6Do the assumptions matter?29 of 73 hosts change class. The naive rule never changes.

Run it locally

Docker is the only requirement. The dashboard reads the stored results.

git clone https://github.com/Mohamad-Talha-E/QuantumAudit.git
cd QuantumAudit
docker compose build
docker compose up -d dashboard
# open http://localhost:8000

Verify the suite with docker compose run --rm tools python -m pytest tests -q. Expected result: 93 passed.
